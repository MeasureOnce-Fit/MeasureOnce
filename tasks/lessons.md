# MeasureOnce working lessons

- Pre-created test identities do not complete account onboarding. Verify guest, new-user registration, email confirmation, first login without a principal, and returning-user flows separately; distinguish email delivery evidence from pre-verified synthetic tests.
- Public email signup depends on remote Auth redirect and SMTP settings. Test a real signup before calling the journey complete, and map redirect rejections to the exact operator action instead of a generic retry message.
- Prototype authentication policy must be explicit before account UI ships. When the intended experience is disposable test access, avoid confirmation-email copy and retain server-owned shopper/operator role separation.
- Shared brand words must retain identical typography at every breakpoint. Never shrink ONCE to a label or hide it on mobile; only its accent color differs.
- In browser auth tests, assert the destination URL pathname. A glob ending in /fit-passport also matches the sign-in page's next=/fit-passport query and can incorrectly advance before authentication finishes.

- An approved landing screenshot is a visual reference, not a substitute for working HTML. Preserve its garment artwork while rebuilding navigation and controls as real elements; never impose a desktop minimum width that clips the page on smaller screens. Check actual screenshots and clicks before deployment.
- Keep the approved page structure explicit: Home holds the welcome and collage; About holds product explanations and demonstrations; Shop Women and Shop Men are separate routes. Department links must open the corresponding page, including links from Fit Passport.

- Derive synthetic shopper coverage from an explicit scenario matrix. A few authentication accounts do not substitute for varied fit profiles; keep account count, scenario count and real-user evidence separate.
- Treat measurement units and measurement kind as first-class data. Never silently equate body circumference, flat garment width, finished garment circumference or a size label.
- The user has requested approval after the execution plan and before application coding. Planning/research may proceed; do not begin implementation until that approval arrives.
- Do not multiply authentication identities by every measurement or preference variation. Model account, fit profile, profile subject, preference and evaluation case separately; one account can own several profiles and each profile can exercise many test cases. Use **additional member profile** as the neutral term; do not encode partner, spouse or household relationship assumptions.
- Each milestone requires its own analysis and decision review. M3 needs researched questions before flow approval; M4 and M5 need approved mockups before code; M6 and M7 need approved evaluation and operations protocols before execution.
- For any user-facing M2 account work, show the interactive mock before connecting production behavior. Keep backend/security implementation moving independently, but do not treat a written design plan as the UI review artifact.
- Preserve MeasureOnce's established Instrument Serif, Manrope, editorial spacing and product layout across new screens. The approved direction excludes blue, green, black-heavy surfaces and bright coral; use a subdued warm off-white, oatmeal, dusty-rose, cognac and deep-plum system unless the user explicitly changes it.
- Do not invent a shopper identity model while designing account UI. For the first retailer integration, the retailer owns authentication; MeasureOnce receives a verified opaque subject and stores retailer-isolated fit data. A shopper-facing MeasureOnce login is out of scope unless the user explicitly approves portable identity later.
- When the user says the existing prototype is visually successful, extend its exact tokens, type, spacing and ecommerce composition. Do not replace it with a trend palette or generic dashboard styling.
- Size labels and equivalence groups are separate. Women's `0` and `2` under `XS` is only one example: model brand-specific alpha, numeric, denim-waist, composite, petite/regular/tall, plus, grouped and market-equivalent configurations while preserving every exact sellable variant and measurement.
- Do not derive a benchmark's inputs or expected outputs from the same generator being evaluated. Freeze literal cases, check exact sizes and regional findings, expose the evidence in a reviewer artifact, and keep independent sign-off visibly pending until another collaborator supplies it.
- A `TRADEOFF` result requires two plausible adjacent sizes with opposing regional advantages and per-option findings. A single measurement falling between two sizes is not enough.
- Known-garment transfer must use the anchor's stored, method-tagged garment geometry and declared wearer-ease transformation. A size label or the anchor's generated body range alone is insufficient evidence.
- Composite size systems need independent axes. Preserve the six source labels, but expand waist/inseam, neck/sleeve, jacket length and petite/regular/tall combinations instead of encoding one diagonal list.
- Never return an exact composite label unless the profile includes evidence for every axis that changes the label. A valid waist alone cannot select an inseam, and chest alone cannot select jacket length.
- A data-only comparison fixture must be executable: it needs a style, exact variants, measurements, compatible ranges and at least one recommendation run. Metadata does not count as engine coverage.
- Keep collaborator signoff in a separate file that evaluation reruns do not overwrite. Bind every approval to a fingerprint of the reviewed input, expected output, relevant catalog data and engine versions so changed content cannot inherit stale approval. Automated contract passes and independent review are different claims.
- Validate enum-like inputs against the declared values and measurement methods against the full version/kind/region identifier; truthy strings and version prefixes are insufficient.
- Run `next build` and `tsc --noEmit` sequentially in this project because both read or regenerate `.next/types`; parallel execution can create a false missing-`routes.js` failure.
- Review actions must save directly from the HTML dashboard and remain editable there. Do not make the collaborator export, download or manually copy a signoff file.
- A fit-contract reviewer must see the human brand/product name, exact sellable size, finished garment measurements, compatible body ranges and any known-garment anchor measurements. Raw variant IDs and result labels alone are not reviewable evidence.
- When a reviewer rejects a ranking, compare the written note with the displayed regional findings before changing the engine. Record the review as complete but unresolved when the named region conflicts with the underlying evidence, and obtain an explicit product rule for which trade-off should rank first.
- In fashion collages, keep every garment visibly independent. Use an irregular white torn-paper seam to crop roughly one quarter of the lead garment and reveal the next garment below; never align a skirt under a shirt in a way that reads as one outfit unless that composition was explicitly requested.
- New MeasureOnce flows must reuse the original prototype's exact design tokens and established fit-overlay treatment. Do not create a parallel palette for milestone review pages; review controls should stay visually secondary to the product experience.
- Garment measurement callout endpoints must land on actual garment pixels after accounting for source-image whitespace, `object-fit` scaling and container padding: waist on the waistband, hip/seat on the fullest upper-hip fabric, and trouser length on an outside leg rather than the inseam gap. Inspect the rendered photograph before presenting labels.
- A product-level “Find my size” action must carry the selected product context into the fit flow. Derive and lock the relevant garment type from the selected item so the shopper only supplies reference-brand and size details instead of classifying the garment again.
- Use the derived garment type to initialize regional fit questions: preselect “Not applicable” for irrelevant regions while leaving the choice editable for unusual garment construction. Do not ask shoppers to manually dismiss obviously unrelated body regions.
- Render each summary from the evidence path the shopper selected. Never describe a known garment as body measurements, or show a default-path recap after the path changes.
- Test service RPCs against the typed JSON contract after deployment, not only in local source. For an idempotent start/apply workflow, expose the pending/accepted state and let a retry resume pending work. Keep private tables private; provide only a narrowly scoped service-role RPC for operational verification.
- In a Next.js browser module, read each NEXT_PUBLIC_ variable through an explicit property before passing it to shared validation. Dynamic lookup through process.env can leave public configuration absent in the Turbopack client bundle; verify the actual browser sign-in after adding or changing any public configuration dependency.
- A production release that depends on both Supabase and an application-session signer must verify the signed-out UI, valid browser-cookie exchange, and protected-profile read after every deployment. A public page returning 200 is not evidence that its authenticated flow is configured.
- When a callout is attached to a product photograph, put the photograph and callouts inside the same aspect-ratio canvas. Positioning pins against the outer layout panel will drift whenever the image is letterboxed. Inspect the deployed rendering after each adjustment.
- The initial retailer integration has one retailer-owned account. Keep credentials on the retailer account page and make Fit Passport a post-login destination; no screen may look like a separate MeasureOnce sign-in.
- Header preference: large centered MEASUREONCE wordmark with ONCE in the original deep terracotta. Place Shop Women, Shop Men, My Fit, Search, Bag and About beneath it, with About last; preserve that reading order on mobile.
- Build known-garment questions from the engine's shared required-region contract, not `criticalRegions` alone. Composite labels can add inseam, neck, sleeve or body-length evidence; filtering anchors or shaping the UI from a narrower list creates an uncompletable loop. Preserve both labelled options and per-option findings when sanitizing a `TRADEOFF` result.
- Never ask for an unknown brand and label as though they can produce a recommendation. Offer an evidence ladder: exact catalog garment, user-measured garment, body measurements, then an explicit preference-only path that abstains from sizing; labels remain descriptive metadata only.
- Before claiming a user-requested flow complete, convert every explicitly stated UI requirement into a named acceptance check and trace it to a test. Passing adjacent engine or browser tests does not cover an omitted control such as a requested brand list.
- A catalog brand list and verified size-reference coverage are different datasets. Brand pickers must enumerate every active brand in the target category, while recommendation eligibility remains an explicit per-brand coverage state. Test every relevant target product, not merely that one reference fixture appears.
- Brand-display migrations need a case-insensitive whole-project scan plus an exact approved-name assertion; preserve stable internal IDs while removing retired names from every rendered review and shopper surface.
- Bind asynchronous fit results to the active fit session. Opening, closing, or submitting a newer fit must invalidate older responses so stale recommendations cannot overwrite the current product.
- A feature that expands a persisted profile contract must ship with its Supabase migration before the frontend is exercised. Verify the deployed protected-profile read and create journey immediately after applying it; local source/schema checks alone cannot prove the hosted database has the required columns and RPC definition.
- When adding a required field through a wrapper around an existing snapshot RPC, make the initial insert valid (for example, with a database default), grant the new overload to `service_role`, qualify returned table fields inside PL/pgSQL, reload Supabase's REST schema cache, and exercise both protected read and create paths live.
- A verified brand/category size reference must also be scoped to the shopper collection or department. Never reuse one generic `M` chart across women’s and men’s targets; test the exact exposed brand, target product, size label, fit observations, and final recommendation in the live browser.
- Verified chart coverage is not complete when one size merely proves the dropdown works. Assert the full ordered size range for every exposed brand, exercise every brand/size pair through the engine, and keep at least one repeatable browser matrix that waits for the evaluated result rather than the loading shell.
- Keep Fit Passport known-size selection ordered by its data dependencies: collection, clothing type, brand, then size. When verified chart coverage changes, migrate only exact collection-scoped legacy matches, verify the persisted evidence badge, and run the saved-fit result; a dropdown fix alone does not update old `remembered_size_context` records.
- Load only the configuration required by a prototype sign-up session. A strict external-assertion key parser must not make account creation unavailable when that key is unrelated to the session exchange.
- Saved-fit recommendations must be requested when the shopper opens a product and must disclose whether they relied on a verified saved size reference or body measurements; testing the questionnaire alone does not prove this product-detail journey.
